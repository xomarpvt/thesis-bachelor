\subsection{Classifier} % 5.2.1

Inizialmente, vengono calcolati gli hash del file binario, tra cui il digest SHA-256, mediante la libreria \texttt{hashlib}\footnote{\url{https://docs.python.org/3/library/hashlib.html}}. L'hashing riveste un ruolo fondamentale nell'analisi del malware, poiché consente di identificare univocamente un campione tramite una \textit{fingerprint}. L'hash può quindi essere utilizzato come etichetta identificativa del file e, soprattutto, come riferimento per condividere e confrontare informazioni tra reverse engineer. Ad esempio, il digest calcolato può essere impiegato per verificare la presenza del campione all'interno di database di malware o di servizi online di \textit{threat intelligence} \cite{sikorski2012malware}.

\subsubsection{Virus Total}

A questo scopo viene utilizzato il servizio VirusTotal\footnote{\url{https://virustotal.com}}, che consente di sottoporre un file all'analisi di numerosi \textit{antivirus engine}, fornendo un report che elenca i rilevamenti di attività malevola, le informazioni tecniche sul campione e che suggerisce un nome e una categoria di \textit{Malware Threat}.

Nell'implementazione è stata utilizzata l'API pubblica di VirusTotal, disponibile gratuitamente entro specifici limiti di utilizzo e destinata a un impiego non commerciale e non professionale \footnote{\url{https://docs.virustotal.com/reference/overview}}. Per ottimizzare il processo, viene prima effettuata una richiesta HTTP GET utilizzando l'hash SHA-256 del file, verificando se il campione è già presente nel database. In caso di esito positivo, viene recuperato direttamente il report associato; in caso contrario, il file viene caricato tramite una richiesta HTTP POST e sottoposto ad analisi, al termine della quale viene recuperato il relativo report.

Le informazioni ottenute vengono utilizzate per determinare la natura del campione mediante un'euristica basata sul numero assoluto di rilevamenti e sulla percentuale di antivirus engine che lo classificano come malevolo. Quando il campione non supera la soglia prefissata viene scartato e l'analisi termina.

\subsubsection{YARA}

Per l'individuazione della famiglia del malware si ricorre invece all'applicazione delle \emph{YARA rules}. YARA è un progetto open source utilizzato per identificare e classificare campioni di malware attraverso regole che definiscono specifiche caratteristiche ricercabili all'interno dei file analizzati. Tali regole combinano pattern, come stringhe e sequenze di byte, con condizioni logiche che determinano quando una regola corrisponde al campione esaminato \cite{sikorski2012malware}. % Appendice B, pagina 475

Per questa implementazione viene utilizzato YARA-X \footnote{\url{https://github.com/VirusTotal/yara-x/}}, insieme alla relativa libreria Python \footnote{\url{https://virustotal.github.io/yara-x/docs/api/python/}}. YARA-X è una nuova implementazione del linguaggio di YARA, progettata per mantenere la compatibilità con le regole esistenti, introducendo anche correzioni e nuove funzionalità.

Il \textsc{Classifier} carica quindi l'insieme delle YARA rules definite, con regole specifiche per ciascuna famiglia di malware supportata, e le compila, preparandole per l'analisi del file binario. Successivamente, il campione viene confrontato con tutte le regole caricate, alla ricerca di una corrispondenza. Nel caso venga individuato un match, la regola corrispondente permette di individuare la famiglia del campione, fornendo al \textsc{SRE Agent} un informazione aggiuntiva a supporto dell'analisi.

è arrivato il momento di determinare se not-stripped o stripped. Questo si potrebbe teoricamente anche fare dal classifier, estraendo tale informazione dal magic del file. Però qui basta usare una funzione dedicata sempre passando per API framework: indicatore euristico.

% Tramite le API del framework SRE è possibile ottenere la lista delle funzioni. La presenza prevalente di questi nomi può quindi essere utilizzata come indicatore per determinare se un file è stripped.

Se il file stripped si parte con prima attività \textsc{RenamingTask}. La prima è pensata per partire da zero, la seconda invece opera su un binario a cui è stato già fatto un lavoro di rinomina, espandendo, ma anche revisionando.

Dal punto di vista di questa implementazione, sono fatte con due cicli agent consecutivi. La start viene fatta sempre e la continue una sola volta viene fatta quando non tutti i nomi sono stati recuperati da start. Queste in teoria potrebbero anche essere eseguite in parallelo, per semplicità sono lasciate in sequenza consecutive.

\subsection{Ghidra MCP Server} % 5.3.3 (bridge)

Il server MCP del software \texttt{ghidra-mcp} è implementato mediante il modulo \texttt{bridge\_mcp\_ghidra}, sviluppato in Python utilizzando la libreria FastMCP \footnote{\url{https://gofastmcp.com/}}. Una caratteristica interessante del modulo è l'organizzazione dei tool in gruppi semantici, che permette di gestire in maniera selettiva l'insieme delle funzionalità esposte al LLM. In modalità standard, il server rende disponibili tutti i gruppi di tool; tuttavia, considerata l'ampiezza del catalogo, il software può essere eseguito anche in modalità \textit{lazy}, caricando inizialmente solo i gruppi di tool principali. \section{Ambiente Sandbox} % 5.4

La sandbox di SRE viene realizzata mediante un ambiente di esecuzione containerizzato, utilizzando Docker per la creazione, la configurazione e la gestione dei container.

La containerizzazione è una tecnica di isolamento a livello di sistema operativo che consente di eseguire un'applicazione e le relative dipendenze all'interno di un ambiente isolato. Rispetto alle macchine virtuali, che richiedono l'esecuzione di un intero sistema operativo guest, i container rappresentano un approccio più leggero per ottenere ambienti di esecuzione separati \cite{docker2026container}.

Nel contesto della \textsc{SRE Sandbox}, Docker fornisce i meccanismi necessari alla creazione e alla configurazione dei container, consentendo di controllarne il filesystem, l'accesso alla rete e le risorse computazionali disponibili. Queste caratteristiche permettono di configurare l'ambiente in modo coerente con i requisiti di isolamento e sicurezza individuati durante la fase di progettazione.

\subsection{Configurazione} % 5.4.1 del Dockerfile

La configurazione dell'ambiente \textsc{SRE Sandbox} è definita mediante un \textit{Dockerfile}, che specifica l'immagine di base, le dipendenze e le impostazioni necessarie al funzionamento del container. L'immagine utilizzata è basata su Python 3.13 e Debian Slim \footnote{\url{https://hub.docker.com/_/python}}, così da fornire un ambiente contenuto, ma sufficientemente completo da permettere al LLM di svolgere le operazioni richieste.

Per consentire lo scambio controllato dei \textsc{Sandbox Files}, una directory dell'host viene montata all'interno del container con permessi di lettura e scrittura. Infine, vengono imposti limiti alle risorse computazionali disponibili, in termini di memoria e capacità di elaborazione.

\section{MCP Client} % 5.5

Per i due MCP client, \textsc{Sandbox MCP Client} e \textsc{Ghidra MCP Client}, è stata definita una classe di base comune, \texttt{BaseMCPClient}, responsabile dell'instaurazione e del mantenimento della connessione con il rispettivo MCP server mediante il metodo di trasporto \textit{stdio}. Il ciclo di vita della connessione viene gestito attraverso un contesto asincrono, all'interno del quale viene inizializzata una \texttt{ClientSession} fornita dal \textit{Python MCP SDK} \footnote{\url{https://py.sdk.modelcontextprotocol.io/}}. La classe espone le due operazioni fondamentali per l'interazione con il server: la consultazione dei tool disponibili, con \texttt{list\_tools}, e la loro invocazione, con \texttt{call\_tool}.

\subsection{LLM-MCP Client} % 5.5.1 Tool Parsing

La classe \texttt{BaseMCPClient} viene ulteriormente estesa da \texttt{LLMMCPClient}, che introduce il livello di integrazione con il LLM e si interpone tra la gestione della connessione MCP e le implementazioni specifiche dei singoli client. In particolare, i tool esposti dai server MCP vengono convertiti nel formato utilizzato dal meccanismo di \textit{function calling} delle OpenAI API \footnote{\url{https://developers.openai.com/api/docs/guides/function-calling}}, includendo le informazioni relative al nome, alla descrizione e ai parametri richiesti.

Entrambi i client specifici estendono quindi \texttt{LLMMCPClient}, ereditandone le funzionalità comuni. Poiché i server sono stati implementati secondo modalità di interazione uniformi e già predisposte all'utilizzo da parte di LLM, non è stato necessario introdurre ulteriori funzionalità, come una formattazione specifica per le risposte, nelle classi derivate.

A completamento di questa struttura, una classe dedicata fornisce un meccanismo per la registrazione dei client MCP e dei relativi tool. Essa consente di applicare opzionalmente ai nomi dei tool un \textit{namespace}, costituito da un prefisso identificativo del client MCP, e di selezionare, specificandone i nomi, un sottoinsieme dei tool disponibili. In questo modo, i tool esclusi possono essere nascosti dall'insieme di strumenti esposti al LLM. % LLMMCPRegistration

Nel complesso, queste componenti costituiscono un livello di astrazione comune per i diversi client MCP, semplificando l'integrazione con il LLM. I tool forniti dagli ambienti di esecuzione possono così essere esposti in modo uniforme e utilizzati attraverso il meccanismo di \textit{tool calling} previsto.

\section{LLM} % 5.6

\subsection{Server} % 5.6.1

Il LLM utilizzato dall'applicazione viene eseguito tramite un'istanza esterna di \textit{vLLM} \footnote{\url{https://vllm.ai/}}, un framework open source progettato per l'inferenza e il \textit{serving} di LLM. Il server vLLM è quindi responsabile dell'esecuzione del modello e della gestione delle richieste di inferenza provenienti dall'applicazione.

L'interfaccia esposta da vLLM è compatibile con le API OpenAI \footnote{\url{https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/}}, permettendo all'applicazione di interagire con il modello attraverso un'interfaccia standardizzata. Questa configurazione consente di utilizzare LLM eseguiti localmente, senza vincolare l'applicazione a uno specifico modello o fornitore esterno.

\subsection{Client} % 5.6.2

Il \texttt{LLM Client} rappresenta il componente responsabile dell'interazione tra \textsc{SRE Agent}/\textsc{Code Agent} e il LLM, integrando inoltre gli strumenti esposti attraverso i client MCP.

Alla sua inizializzazione vengono specificati i client MCP con i quali il LLM può interagire, quindi gli strumenti da essi esposti vengono raccolti e salvati in una struttura di risoluzione. Questa associazione permetterà successivamente di individuare, a partire dal nome del tool richiesto dal LLM, il client MCP responsabile della sua gestione. Il \texttt{LLM Client} si occupa quindi anche dell'invocazione dei tool, inoltrando ciascuna tool call al client MCP corrispondente e recuperandone il risultato.

Il componente permette inoltre di configurare i \textit{sampling parameters} (parametri di campionamento), ovvero le variabili utilizzate per controllare le caratteristiche della generazione del testo, tra cui \texttt{temperature}, \texttt{top\_p}, \texttt{top\_k}, \texttt{min\_p}, \texttt{presence\_penalty} e \texttt{repetition\_penalty}. È inoltre possibile scegliere la modalità di ragionamento del LLM, abilitandola o disabilitandola tramite \texttt{preserve\_thinking} e specificandone il livello mediante \texttt{reasoning\_effort}.

Sono quindi messi a disposizione metodi per effettuare richieste singole, con o senza tool, al LLM mediante \textit{chat completion}, secondo l'interfaccia prevista dalle OpenAI API \footnote{\url{https://developers.openai.com/api/reference/resources/chat}} e dal relativo SDK Python \footnote{\url{https://pypi.org/project/openai/}}.

% Le richieste possono essere effettuate con o senza l'utilizzo dei tool.
% I parametri di campionamento, così come eventuali altri parametri supportati dal client, possono inoltre essere specificati o sovrascritti per la singola richiesta.

Infine, il componente fornisce la struttura di base dell'agente che viene utilizzata dal \textsc{SRE Agent}. Questa è realizzata mediante un ciclo iterativo che gestisce autonomamente lo stato della conversazione, l'invocazione del LLM, l'esecuzione dei tool e l'inserimento nel contesto dei risultati ottenuti, proseguendo l'elaborazione fino al raggiungimento dell'obiettivo. L'implementazione segue il paradigma \textit{ReAct}, alternando le fasi di ragionamento e di azione, preservando il ragionamento prodotto dal LLM, affidando al modello la selezione dei tool ed eseguendo sequenzialmente le tool call.

All'interno del ciclo di esecuzione non sono stati introdotti meccanismi di compattazione del contesto, così da mantenere la massima fedeltà alla cronologia dell'esecuzione e non perdere informazione. Sebbene questa scelta possa comportare il raggiungimento del limite della finestra di contesto, tale eventualità non si è rivelata problematica per gli utilizzi considerati nell'ambito di questa implementazione.

\subsubsection{Logging}

A supporto dell'esecuzione dell'agente, sono state implementate le funzionalità di logging individuate durante la fase di progettazione, secondo due modalità distinte e complementari.

La prima è orientata alla conservazione completa dell'esecuzione e produce un output strutturato in formato JSON, conforme al formato utilizzato dalle OpenAI API \footnote{\url{https://developers.openai.com/api/reference/resources/chat}}. Il log contiene l'intera cronologia della conversazione, includendo in particolare le tool call effettuate e i relativi risultati. La struttura adottata permette quindi di analizzare oppure importare e continuare a elaborare successivamente la singola esecuzione

La seconda modalità è invece orientata alla consultazione da parte dell'utente e presenta una sintesi leggibile dell'esecuzione. In particolare, vengono riportati il prompt iniziale e, per ciascun passo, alcune statistiche relative all'elaborazione (numero di token e tempo di esecuzione parziali), insieme al ragionamento, alle tool call e alle risposte prodotte dal LLM. I risultati restituiti dai tool non vengono inclusi in questa visualizzazione, in modo da mantenere il focus sulla Chain of Thought sviluppata dal LLM.

\section{MessageSchema} % 5.7

Come individuato già a partire dalla fase di analisi dei requisiti, è necessario definire uno schema comune per i messaggi restituiti dal \texttt{Python Module}. A questo scopo è stato adottato \textit{JSON Schema}, particolarmente adatto a descrivere e verificare strutture dati rappresentate in formato JSON.

JSON Schema è un linguaggio dichiarativo progettato per descrivere la struttura e i vincoli dei dati rappresentati in formato JSON. Attraverso un insieme di parole chiave consente di specificare in modo chiaro le proprietà dei dati, con i tipi di dati consentiti, i campi obbligatori, i formati richiesti e altre restrizioni strutturali \cite{jsonschema2020json}.

L'utilizzo di JSON Schema risulta particolarmente adatto per due motivi. Il primo è la possibilità di verificare la conformità di un documento JSON, denominato \textit{instance}, rispetto a uno schema mediante un apposito \textit{validator}, confrontando automaticamente la struttura e i contenuti dell'istanza con i vincoli definiti nello schema. Il secondo riguarda il suo utilizzo come forma di documentazione: lo schema fornisce infatti una descrizione esplicita della struttura e dei vincoli dei dati, comprensibile sia dallo sviluppatore, sia da un LLM.

\subsection{Message Classification} % 5.7.1

Tra i costrutti messi a disposizione da JSON Schema rientra \texttt{oneOf}, che consente di specificare che un'istanza deve risultare valida rispetto a uno e un solo schema tra quelli definiti. Tale costrutto può essere sfruttato, nell'ambito dell'applicazione considerata, per distinguere semanticamente i messaggi catturati dall'infrastruttura di C\&C in diverse tipologie. In questo modo, oltre a facilitare l'interpretazione dei messaggi da parte dell'utente, è possibile associare a ciascuna tipologia uno schema specifico, definendo ricorsivamente i campi appropriati in funzione della classificazione del messaggio.

Per l'implementazione considerata sono state pertanto individuate le seguenti quattro categorie:

\begin{description}
    \item[ACK] identifica i messaggi mediante i quali il server C\&C richiede l'invio di un acknowledgment in risposta a un precedente messaggio.
    \item[Attack] identifica i messaggi contenenti istruzioni relative all'esecuzione di un attacco.
    \item[Heartbeat] identifica i messaggi utilizzati per il mantenimento della connessione e per il keepalive del traffico.
    \item[Command] identifica i messaggi di servizio o generici che non rientrano nelle categorie precedenti, oppure i messaggi per i quali non si è in grado di effettuare una classificazione più specifica.
\end{description}

\subsection{JSON Schema} % 5.7.2

Lo schema realizzato, conforme allo standard JSON Schema Draft 2020-12 \footnote{\url{https://json-schema.org/draft/2020-12/json-schema-core.html}}, è riportato integralmente nelle appendici. Al primo livello dello schema vengono memorizzati il \textit{timestamp} di ricezione del messaggio e l'indirizzo IP sorgente. Inoltre, è presente un campo dedicato alla classificazione del messaggio, secondo le tipologie introdotte nella sezione precedente, a cui segue uno schema annidato contenente le informazioni specifiche relative alla tipologia individuata. % \Cref{fig}

Per ciascuna categoria sono quindi definiti vincoli e proprietà specifici. I messaggi \texttt{ACK} contengono l'informazione associata allo stato della richiesta di acknowledgment, mentre i messaggi \texttt{Heartbeat} riportano un numero di sequenza lato server e, opzionalmente, il tempo di connessione del bot. I messaggi \textit{Command} includono invece il \textit{payload} originale e, quando è possibile determinarla, una stringa che identifica la tipologia del comando. Infine, tutte le tipologie di messaggio prevedono un campo opzionale \texttt{notes}, destinato a contenere informazioni aggiuntive sotto forma di stringa oppure valorizzato a \texttt{null}.

La tipologia \texttt{Attack} è quella caratterizzata dalla struttura più articolata. Per ciascun messaggio vengono infatti memorizzati il codice identificativo e il nome dell'attacco, il protocollo di rete coinvolto e la durata dell'esecuzione. Lo schema permette inoltre di rappresentare gli argomenti forniti all'attacco attraverso il numero di elementi (\texttt{argc}) e i relativi valori (\texttt{argv}). Infine, vengono memorizzati il numero dei bersagli coinvolti e il relativo elenco di indirizzi IP di destinazione.

\subsubsection{IP Schema}

Lo schema include anche un array dedicato alle informazioni relative agli indirizzi IP coinvolti negli attacchi, che può rimanere vuoto qualora non siano disponibili ulteriori informazioni sui bersagli. Per ciascun indirizzo è possibile memorizzare dati relativi alla sua localizzazione e alla rete di appartenenza.

In particolare, lo schema consente di rappresentare informazioni geografiche a diversi livelli, dal continente fino alla città, oltre a dati di geolocalizzazione quali latitudine, longitudine e \textit{timezone}. Sono inoltre previste informazioni sulla rete di appartenenza dell'indirizzo IP, con la relativa notazione CIDR e i principali attributi dell'\textit{Autonomous System} (AS), quali numero identificativo (ASN), nome e dominio. Lo schema include infine informazioni relative alla risoluzione DNS e ad altri eventuali metadati associati all'indirizzo.

\subsubsection{IP Lookup}

L'arricchimento dei dati relativi agli indirizzi IP deve essere gestito dai singoli \textsc{Python Module}; tuttavia, per evitare la duplicazione del codice e garantire uniformità nelle modalità di recupero delle informazioni, questa funzionalità è stata centralizzata in un componente dedicato, \texttt{IPLookup}, condiviso tra i diversi moduli e richiamabile quando necessario.

Il modulo \texttt{IPLookup} implementa una classe progettata per interrogare database locali in formato \texttt{.mmdb} (\textit{MaxMind DB}), quali i database \textit{IPinfo Lite} \footnote{\url{https://ipinfo.io/developers/ipinfo-lite-database}} e \textit{GeoLite2}, nelle varianti \textit{City}, \textit{Country} e \textit{ASN} \footnote{\url{https://dev.maxmind.com/geoip/docs/databases/}}, così da estrarre le informazioni associate agli indirizzi IP. L'interazione con questi dataset avviene tramite l'apposita libreria Python \textit{maxminddb} \footnote{\url{https://maxminddb.readthedocs.io/en/latest/}}, mentre i database sono aggiornati frequentemente e distribuiti gratuitamente, secondo le relative condizioni di licenza \footnote{\url{https://ipinfo.io/developers/ipinfo-lite-database} (CC BY-SA 4.0)} \footnote{\url{https://www.maxmind.com/en/geolite/eula} (EULA con CC BY-SA 4.0)}.

\section{Code Templates} % 5.8

% \subsection{Aggiornamento BotNetInterface} % 5.8.0

Come suggerito durante la fase di progettazione, per separare le responsabilità relative alla cattura e all'elaborazione dei messaggi vengono utilizzati due file distinti, dedicati rispettivamente alla fase di cattura e a quella di parsing dei messaggi secondo il \textsc{MessageSchema}. Il punto di ingresso principale è il \textsc{BotNet Module}, che implementa la \texttt{BotNetInterface}.

Per rappresentare a livello di codice la classificazione dei messaggi viene utilizzata un'enumerazione Python \footnote{\url{https://docs.python.org/3/library/enum.html}}, \texttt{MessageType}, che definisce le quattro tipologie di messaggio individuate nello schema.

Infine, poiché il primo modulo utilizza funzionalità di logging, mentre il secondo dipende dalla classe centralizzata \texttt{IPLookup}, alla \texttt{BotNetInterface} è stato aggiunto un costruttore che permette di fornire tali oggetti durante l'inizializzazione. L'interfaccia completa è riportata nelle appendici.

\subsection{BotNet Module} % 5.8.1

Il template completo del modulo è riportato nell'appendice. La responsabilità del \textsc{BotNet Module} consiste nell'implementare i metodi definiti dalla \texttt{BotNetInterface}, rispettandone i contratti, e nel fornire lo scheletro del modulo principale che dovrà essere completato in funzione dello specifico protocollo analizzato. Il template definisce pertanto le funzioni del modulo e le modalità con cui le diverse fasi dell'interazione con l'infrastruttura C\&C devono essere implementate.

La struttura del modulo può essere descritta secondo le seguenti aree:

\begin{description}
    % Attributi e costanti di classe.
    \item[Attributi di classe.] Contengono i parametri statici specifici del protocollo, quali l'\textit{hostname} o l'indirizzo IP del server C\&C, le sequenze utilizzate durante l'handshake, i messaggi o i parametri relativi agli acknowledgment e agli heartbeat e, più in generale, i valori costanti necessari alla comunicazione.
    
    \item[Costruttore \texttt{\_\_init\_\_}.] Inizializza le risorse e i componenti necessari all'esecuzione del modulo, tra cui il \textit{socket}, il \textit{buffer} utilizzato per la ricezione dei dati, il \textit{logger} e il modulo \texttt{MessageParser}, responsabile dell'elaborazione dei messaggi.
    
    \item[Metodo \texttt{connect}.] Stabilisce la connessione con l'endpoint C\&C e avvia, mediante il metodo dedicato \texttt{authentication}, la sequenza di inizializzazione prevista dal protocollo. Questa fase permette al modulo di registrarsi presso il server di C\&C, simulando il comportamento del dispositivo di una potenziale vittima.
    
    \item[Metodo \texttt{sniff}.] Rimane in ascolto dei dati provenienti dal server C\&C e gestisce, quando previsto, l'invio periodico dei messaggi di keepalive tramite il metodo dedicato \texttt{heartbeat}. I dati ricevuti vengono eventualmente sottoposti a un pre-processing tramite \texttt{preprocess\_stream} e sono successivamente aggiunti al buffer. Da quest'ultimo, tramite \texttt{extract\_packets}, vengono estratti i pacchetti, che possono essere quindi decodificati o decifrati tramite \texttt{decode\_packet}. Dai pacchetti elaborati vengono estratti i singoli messaggi mediante \texttt{extract\_messages}, per poi essere classificati secondo il \texttt{MessageType} tramite \texttt{get\_message\_type}. Inoltre, quando previsto dal protocollo, \texttt{handle\_message} permette di eseguire l'azione attesa dal server, in risposta al messaggio ricevuto, come ad esempio l'invio di un acknowledgment. Il parsing del contenuto del messaggio viene invece demandato al \texttt{MessageParser} tramite il metodo \texttt{parse\_message}, che produce un dizionario Python, successivamente restituito tramite \texttt{yield}. L'utilizzo di un dizionario garantisce inoltre la compatibilità diretta con la successiva serializzazione in formato JSON, per la quale sarà sufficiente usare la funzione \texttt{json.dumps} \footnote{\url{https://docs.python.org/3/library/json.html}}.
\end{description}

Per rendere il template del modulo direttamente utilizzabile nella successiva generazione del codice, tutti i metodi sono accompagnati da \textit{docstring} che ne descrivono il contratto, il comportamento atteso e le operazioni che devono essere implementate. In questo modo, nei prompt forniti al LLM è sufficiente riportare una descrizione più generale del protocollo, senza dover specificare nuovamente tutti i dettagli tecnici. Nel template sono inoltre esplicitamente indicati gli eventi per i quali è previsto il logging, realizzato con l'omonima libreria Python \footnote{\url{https://docs.python.org/3/library/logging.html}}, così da mantenere coerente anche questo aspetto nella versione finale del modulo.

Una caratteristica particolare del template è l'implementazione dei metodi ausiliari mediante la keyword \texttt{pass}, utilizzata come \textit{placeholder}, oppure restituendo invariati gli oggetti ricevuti. Questa scelta permette di esplicitare al LLM quali funzionalità sono opzionali e dipendenti dallo specifico protocollo: se una determinata funzionalità è prevista dal protocollo, allora il relativo metodo dovrà essere sovrascritto implementandone la logica specifica; in caso contrario, il comportamento predefinito del template può essere mantenuto invariato.

\subsection{MessageParser Module} % 5.8.2

Il template completo del modulo è riportato nell'appendice. La responsabilità del \textsc{MessageParser Module} consiste nell'implementare il metodo \texttt{parse\_message}, richiamato dal \textsc{BotNet Module}. Tale metodo esegue il parsing di un messaggio e restituisce un dizionario Python conforme alla struttura definita dal \textsc{MessageSchema}, pronto per essere sottoposto alla relativa validazione.

Il metodo \texttt{parse\_message} provvede inizialmente all'estrazione delle informazioni comuni alle diverse tipologie di messaggio, per poi invocare il metodo dedicato all'elaborazione della specifica categoria: \texttt{parse\_ack}, \texttt{parse\_command}, \texttt{parse\_heartbeat} o \texttt{parse\_attack}. Nel caso dei messaggi di tipo \texttt{Attack}, il parser recupera inoltre le informazioni associate agli indirizzi IP dei bersagli dell'attacco mediante la classe \texttt{IPLookup}.

Il modulo implementa inoltre una logica di fallback nel caso in cui il parsing specifico non abbia esito positivo. Se uno dei metodi dedicati non riesce a interpretare il messaggio o incorre in un errore, questo viene classificato come un messaggio generico \texttt{Command}, garantendo comunque la produzione di un risultato conforme allo schema previsto.

Anche per il \textsc{MessageParser Module} valgono gli stessi principi già adottati per il \textsc{BotNet Module} in merito alle descrizioni tramite docstring e alle modalità di implementazione.

\section{Prompt Archive} % 5.9 (Prompt Engineering)

In questa sezione vengono presentati i prompt utilizzati nei due componenti principali del sistema, ossia il \textsc{SRE Agent}, per le attività di \textit{Renaming} e \textit{Reversing}, e il \textsc{Code Agent}. Per ciascuna di queste attività vengono dapprima descritti il \textit{System Prompt} e successivamente gli \textit{User Prompt} specifici. I prompt completi sono riportati nelle appendici.

Per aggiungere dinamicamente ai prompt le informazioni necessarie alle diverse attività viene utilizzato un meccanismo di \textit{context injection}, basato su placeholder che possono essere sostituiti con il contenuto richiesto. Questo meccanismo viene utilizzato sia per i materiali di riferimento forniti al \textsc{Code Agent}, sia, nel caso del \textsc{SRE Agent}, così da poter includere nel prompt, quando disponibile, il contenuto della knowledge base.

\subsection{Renaming} % 5.9.1

\begin{description}
    \item[System Prompt.] Definisce il ruolo del LLM come analista di malware specializzato in SRE e analisi binaria, con particolare attenzione alla ricostruzione della logica di programmi stripped e al renaming delle funzioni. Richiede di identificare sistematicamente lo scopo delle funzioni, ricostruirne le relazioni e proporre nomi coerenti sulla base di evidenze verificabili. Il prompt stabilisce inoltre l'utilizzo delle funzionalità di analisi statica del \textsc{SRE Framework}, sfruttando informazioni quali disassembly, decompilazione e cross-reference per supportare le decisioni di ridenominazione.
    
    \item[Start Prompt.] Definisce il compito di ridenominazione delle funzioni all'interno di un binario stripped, partendo dall'identificazione della funzione \texttt{main} e procedendo ricorsivamente a partire da essa. L'attività principale consiste nel ridenominare le funzioni e, quando necessario, anche i parametri delle funzioni e le variabili locali, così da facilitare le successive attività di analisi. Il prompt suggerisce quindi i tool da utilizzare per effettuare le ridenominazioni. Infine, richiede di basare le ridenominazioni sulle evidenze raccolte durante l'analisi, riportando il ragionamento seguito e il relativo livello di confidenza in un breve output che riepiloga le attività svolte.
    
    \item[Continue Prompt.] Definisce il compito di verificare e migliorare le ridenominazioni già effettuate su funzioni, parametri e variabili, individuando quelle inesatte e correggendole quando necessario. Il prompt richiede inoltre di identificare ulteriori opportunità di ridenominazione, cercando sempre di privilegiare gli elementi che hanno un impatto maggiore sulla comprensione del malware ed evitando di introdurre nomi potenzialmente fuorvianti. Rimangono invariate rispetto al prompt precedente le indicazioni relative ai tool, ai principi di analisi e all'output da produrre.
\end{description}

\subsection{Reversing} % 5.9.2

\begin{description}
    \item[System Prompt.] Definisce il ruolo del LLM come analista di malware specializzato in SRE e analisi binaria. Richiede di produrre risultati tecnici rigorosi, precisi e verificabili, basando ogni conclusione su evidenze direttamente osservabili nel binario e indicando esplicitamente il livello di confidenza tra fatto verificato, ipotesi analitica e informazione sconosciuta. Il prompt stabilisce inoltre l'utilizzo combinato delle funzionalità di analisi statica del \textsc{SRE Framework} e degli strumenti disponibili all'interno della \textsc{Sandbox} per validare ipotesi, estrarre informazioni, analizzare dati offuscati e automatizzare attività ripetitive.
    \item[Transport Prompt.] Definisce il compito di analizzare e documentare il \textit{Transport Layer} del malware, con particolare attenzione al recupero dell'infrastruttura C\&C e all'inizializzazione della connessione. Il prompt richiede di ricostruire le modalità con cui vengono ottenuti l'indirizzo e la porta del server C\&C, incluse eventuali tecniche di offuscamento, cifratura o l'utilizzo di una tabella di stringhe, e di descrivere il relativo protocollo e ciclo di connessione. Infine, richiede di produrre una specifica tecnica completa, sufficientemente dettagliata per la comprensione umana e direttamente utilizzabile per la successiva implementazione.
    \item[Communication Prompt.] Definisce il compito di analizzare e documentare il \textit{Communication Layer} del malware, con particolare attenzione alle fasi di autenticazione e instaurazione della sessione C\&C e al successivo ciclo di elaborazione dei comandi. Il prompt richiede di individuare e ricostruire i meccanismi di autenticazione e crittografia, il formato e il parsing dei messaggi, la gestione dei comandi e le modalità di mantenimento della sessione.  Le indicazioni relative agli standard di analisi e alla struttura e al contenuto dell'output rimangono invariate.
\end{description}

\subsection{Code Agent} % 5.9.3

\begin{description}
    \item[System Prompt.] Definisce il ruolo del LLM come agente specializzato nella generazione di codice Python per moduli di sicurezza di rete. Richiede la produzione di codice completo ed eseguibile, conforme alle specifiche, alle informazioni e ai template forniti. Il prompt descrive inoltre le modalità di estrazione delle informazioni a partire dalla documentazione fornita e stabilisce gli standard di implementazione e qualità del codice da seguire. In particolare, richiede l'utilizzo di Python 3.11+, l'adozione di buone pratiche di sviluppo, con la produzione di codice chiaro, oltre a una gestione adeguata delle eccezioni e del logging.

    \item[BotNet Prompt.] Definisce il compito di generazione del modulo di cattura, specificando che l'implementazione deve essere contenuta in un singolo file e deve ricostruire i layer di comunicazione e trasporto della botnet. Il prompt fornisce quindi i materiali di riferimento, ciascuno affiancato da una breve descrizione: la \texttt{BotNetInterface}, i \texttt{SRE Reports}, il template del \texttt{BotNet Module} e l'enumerazione \texttt{MessageType}. Vengono successivamente definiti i requisiti per l'implementazione dei metodi \texttt{connect} e \texttt{sniff}, specificando in generale il comportamento atteso. Infine, si richiede di rispettare il template esistente e di implementare esclusivamente le funzionalità previste dalla specifica, escludendo qualsiasi comportamento offensivo e restituendo in output il file completo.

    \item[MessageParser Prompt.] Poiché questa generazione segue quella del \texttt{BotNet Module}, il prompt si limita a estendere i materiali di riferimento con il \texttt{MessageSchema} e il template del \texttt{MessageParser}. Il compito definito è la generazione del modulo di parsing, il cui punto di ingresso è rappresentato dal metodo \texttt{parse\_message}, responsabile di indirizzare i messaggi verso i parser specifici. Viene inoltre richiesto di utilizzare il tipo di messaggio generico \texttt{Command} come \textit{fallback} in caso di errore durante il parsing. Anche in questo caso, il prompt richiede il rispetto del template, delle richieste definite e del formato di output previsto.
    
    % \texttt{IPSchema} viene escluso in quanto non necessario per il \texttt{MessageSchema}
\end{description}
